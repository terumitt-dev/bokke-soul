# tools

点群や標高グリッドを、Godot で歩けるメッシュ (GLB) に変換するスクリプト。

| スクリプト | 入力 | 向いているデータ |
|---|---|---|
| `pointcloud_to_mesh.py` | LAS / LAZ / PLY の点群 | 建物や壁などの立体。ボクセルの表面にするので角ばる |
| `dem_to_mesh.py` | 「東 北 標高」の等間隔グリッド (テキスト) | 地形。格子を三角形にするので滑らかで、面が少ない |

## セットアップ

```
python3 -m venv .venv
.venv/bin/pip install -r tools/requirements-dev.txt
```

## 使い方

```
.venv/bin/python tools/pointcloud_to_mesh.py data/raw/input.laz game/assets/world.glb --voxel 0.5
```

| オプション | 意味 | 既定値 |
|---|---|---|
| `--voxel` | ボクセルの大きさ (メートル)。小さいほど細かく、重くなる | 0.5 |
| `--min-points` | ボクセル内の点がこれ未満なら捨てる (散らばったノイズ対策) | 3 |
| `--min-component` | つながったボクセルがこれ未満の塊は消す (宙に浮いたノイズ対策) | 50 |
| `--crop XMIN YMIN XMAX YMAX` | XY の範囲を切り出す。大きな点群は先に絞る | なし |

対応形式は LAS / LAZ / PLY。

出力は GLB と、同じ場所の `.json` (元の原点とボクセルの大きさ)。GLB は原点付近に作り、軸も Godot 向け (Y 上向き) に入れ替えています。実際の測量座標に戻したい時は、GLB の頂点 `(x, y, z)` を `(x, -z, y)` に直してから、`.json` の `origin` を足します。`pointcloud_to_mesh.from_godot_coords(vertices, origin)` がこの計算をします。

## 変換の中身

1. 点を読み込む (必要なら範囲を切り出す)
2. ボクセルに割り当て、点が少ないボクセルを捨てる
3. つながりの小さい塊を消す
4. 隣が空いているボクセルの面だけを四角形にして、外向きのメッシュを作る
5. 測量データの Z 上向きを、Godot の Y 上向きに変換して GLB に書き出す。座標は点群の最小値を原点にし、float32 の精度落ちを避ける

見た目は角ばりますが、穴や法線の乱れが出にくく、当たり判定にそのまま使えます。

## 標高グリッドの変換

```
.venv/bin/python tools/dem_to_mesh.py data/raw/xxx_DEM.txt data/processed/terrain.glb --stride 2
```

`--stride` は格子を何個おきに使うか。0.5m 間隔のデータを `--stride 2` にすると 1m 間隔になり、面の数が約 4 分の 1 になります。

変換後のデータは `data/processed/` に置きます (git の管理外)。

### 篝火の場所と、マップの名前

変換のとき、ツールが、**篝火を置く場所**を探して、`.json` の `bonfire` に、測量座標 `[東, 北, 標高]` で書きます。周り (半径 6 m) の傾きがいちばん小さい (平らな) 場所で、マップの端から 40 m 以内と、標高の欠けがある場所は選びません (端は、隣のマップへの出口になるため)。傾きは、`bonfire_slope_deg` (度) で分かります。作り直しても、原点が動いても、同じ場所を指すよう、測量座標で持ちます。

- `--bonfire 東 北` で、場所を決められます (標高がある場所だけ)。
- `--bonfire-margin 40` で、端から離す距離を変えられます。
- `--name 梨本` で、マップの名前を `.json` の `name` に入れます。ゲームは「梨本の篝火」のように使います。
- `.json` の `size` に、GLB の幅・高さ・奥行きが入ります。隣のマップを、原点と大きさから見つけるのに使います。間引き (`--stride`) で、端が、最大 `stride - 1` 格子分 (標高グリッドの間隔が 0.5 m、stride 2 なら 0.5 m) 欠けるので、隣を探す時は、数 m の隙間を許してください。
- 篝火の場所は、**間引く前の格子**で探します。`--stride` を変えても、同じ場所になります。
- `bonfire` は測量座標 `[東, 北, 標高]` です。GLB の座標には、`origin` を引いて、`(x, y, z) = (東 - origin.x, 標高 - origin.z, -(北 - origin.y))` と直して使います (`axes` の説明と同じ向きです)。
- `--crs EPSG:6676` で、座標系を `.json` の `crs` に書けます (別の系のデータを混ぜた時に、気づくため)。
- 場所を手で決めた時 (`--bonfire`) は、`bonfire_slope_deg` は入りません。

## 変換したデータで歩く

取り込みを通さず、起動時に GLB の場所を渡します。データをリポジトリに入れずに試せます。

```
godot --path game res://scenes/world_local.tscn -- --world=/絶対パス/terrain.glb
```

世界の中央の上空から降りて、地面に立ちます。

## 出典の表示

`--credit` と `--license-url` を付けると、GLB の隣の `.json` に出典が書かれ、ゲームのタイトル画面の隅とクレジットに表示されます。出典の表示が必要なデータ (CC BY など) は、必ず付けてください。

同じ `.json` に、世界の名前 `world_id` も書かれます。セーブはこの名前で世界を見分けるので、同じ場所を作り直しても、続きから遊べます。入力の名前にタイル番号 (例: `08OF3006`) があればそれと、入力全体の南西の角から自動で決まり、`--world-id 名前` で自分で決めることもできます (英数字と `.` `_` `-` の 64 文字まで、先頭に `.` は使えません)。切り出し (`--crop`) やメッシュの細かさは、名前に影響しません。ただし、メッシュの原点は動くので、ゲームは、保存した位置を新しい原点に合わせて直します (セーブには、保存した時の世界の形 (原点とメッシュの範囲) も入っていて、同じなら、そのまま信用します。違えば、作り直された世界と見なします。水平の原点や範囲が違う時は、確かめた所の地図は使いません。直した位置が、作り直した世界の範囲の外になる時は、保存した位置は使わず、いつもの始まりになります)。入力の範囲を取り直して、南西の角が変わる時は、名前も変わるので、前のセーブを引き継ぎたければ `--world-id` で、前と同じ名前を渡してください。

```
.venv/bin/python tools/dem_to_mesh.py data/raw/xxx_DEM.txt data/processed/terrain.glb \
  --credit "VIRTUAL SHIZUOKA (静岡県) を加工して作成 / CC BY 4.0" \
  --license-url https://creativecommons.org/licenses/by/4.0/
```

出典の文は、データごとに `docs/data-sources.md` の「出典表示」に合わせます。

## 法線 (面の向き)

書き出す GLB には、頂点の法線を必ず入れます。法線がないと、Godot は全ての面が同じ向きだと見なして、光 (太陽、月、篝火) が、起伏と関係なく、半分の面にしか当たりません。

- 標高グリッド (`dem_to_mesh.py`): 滑らかな法線 (頂点につながる面の平均)
- 点群 (`pointcloud_to_mesh.py`): ボクセルは角ばった形なので、面ごとの法線 (頂点を面ごとに分ける。形は変わらない)

ゲーム側 (`WorldLoader`) も、法線のない GLB を読むと、読み込む時に法線を作ります (古い GLB やほかの GLB のための備えです)。

## 複数のマップを、まとめて変換する

`tools/areas.json` に、使うマップ (タイル) と、その名前、出典を書いてあります。次のコマンドで、全てのマップを、同じ決まり (名前、出典、篝火の場所、世界の名前) で、変換できます。

```
.venv/bin/python tools/build_areas.py data/raw/virtual-shizuoka data/processed --stride 2
```

元データは、`<source>-<タイル番号>/<タイル番号>_DEM.txt` の場所に置きます (`areas.json` の `source` が、フォルダ名の前半です)。名前は、近くの道や歩道の名前に、方角を付けたものです (出典は `docs/data-sources.md`)。

### 隣のタイルとの継ぎ目

`build_areas.py` は、隣り合うタイル (同じ格子の上で、ちょうど隣り合っているもの) の、継ぎ目を閉じます。各タイルに、東と北の隣の、最初の 1 列と 1 行を足してから、メッシュにします。足さないと、隣との間に、格子 1 つ分 (間引くと、もっと) の隙間ができて、つないだ時に、そこへ落ちます。

- 隣のメッシュと、端が、そろいます (`.json` の `origin` と `size` で、隙間は 0 になります)。
- 北東の角は、斜めの隣があればその値、なければ欠けます (その 1 マスだけ、面を作りません)。
- 間引き (`--stride`) をしても、最後の列と行は、必ず使います (割り切れなくても、端が欠けません。最後の間隔だけ、短くなることがあります)。
- 全てのタイルを、同じ格子の線で間引きます。継ぎ目の両側が、同じ位置の頂点を持つので、起伏があっても、継ぎ目に隙間ができません。ただし、東や北の隣のないタイルの、最後の列と行 (領域の外側の端) は、必ず使うので、その先も続く隣の、格子の線に乗らないことがあります。その端の 1 点分は、隙間ができえます (領域の角だけ)。
- `.json` の `origin` と `size` から見た、メッシュの外形の隙間は、0 です。
- 世界の名前 (`world_id`) と、篝火の場所は、継ぎ目を足しても、変わりません (どちらも、足す前の、元のタイルから決めます。隣のタイルの有無で、動きません)。
- 隣のないタイルの、東と北の端は、そのまま、タイルの端です。

### 地域

`areas.json` の `region` (`id` と `name`) を書くと、全てのタイルの `.json` に、`region` (地域の名前) と `region_name` が入ります。ゲームは、同じ `region` のタイルを、まとめて読み込んで、測量座標の位置に並べます。タイルの間は、暗転も読み込みもなく、歩いて渡れます。`region` の `id` は、世界の名前と同じ決まり (英数字と `.` `_` `-` の 64 文字まで) です。何タイルで 1 つの地域にするか、は、決まっていません (いまは、`areas.json` に書いた全てのタイル)。
